# AI 圆桌讨论 Web App — 架构设计文档

> 版本：v1.0 ｜ 技术栈：Python FastAPI + SSE 流式 + DeepSeek API ｜ 目标：可运行、可演示的 MVP

> 📌 **迭代说明（必读）**：本文是最初的设计稿，**保留了原始设计轨迹**。实现过程中有三处与本文不同，最终以代码与 `docs/16-需求逐条验收.md` 为准：
> 1. **调度策略**：本文 §2.1 的"主持人点名制"已改为 **DirectorAgent 自主调度**（嘉宾自主举手 / 补充 / 反驳，主持人只在跑题或超时时插话），以符合需求中"专家自主决定发言顺序、不允许机械轮流"；见 `backend/app/agents/director.py`。
> 2. **Prompt 载体**：本文写的 `prompts/*.yaml`、`schemas/` 目录，实际落地为 `backend/prompts/*.json`（内置 `version` + `changelog`），校验用代码内的轻量解析器，未引入 pydantic 依赖。
> 3. **目录名**：`llm/deepseek_client.py` 实际为 `backend/app/llm/client.py`（内含 httpx 与 stdlib urllib 双通道）。

## 1. 系统总览

```
┌─────────────────────────────── 浏览器（单页前端，Vanilla JS）───────────────────────────────┐
│  首页(圆桌列表)   创建圆桌(主题+嘉宾选择)   直播现场(消息流+思考动画+Transcript侧栏)   历史归档  │
└───────────────┬──────────────────────────────────────────────────────────────────────────┘
                │  HTTP REST（建单/查单）        SSE 长连接（实时流式）
                ▼
┌─────────────────────────────── FastAPI 后端 ───────────────────────────────────────────────┐
│  Route 层        /debates  /debates/{id}  /debates/{id}/stream  /personas                   │
│  Orchestrator    圆桌编排器（核心）：轮次状态机 + 发言人调度 + 主持人控场                     │
│  Agent 层        HostAgent（主持人） / GuestAgent（嘉宾，按 Persona 实例化）                │
│  LLM Client      DeepSeek Chat（OpenAI 兼容协议，stream=True），每嘉宾独立会话上下文          │
│  Persistence     SQLite（debates / messages / personas 三张表），JSON Schema 校验发言        │
└──────────────────────────────────────────────────────────────────────────────────────────┘
```

核心思路：**前端不直接调 LLM**；后端 Orchestrator 负责多智能体调度，把每个 Agent 的流式输出通过 **一条 SSE 通道** 推给前端，前端只做渲染和"思考中"动画。

## 2. 模块设计

### 2.1 Orchestrator（圆桌编排器）— 作业"核心考察点"

职责：决定"下一句谁来说、说什么、何时停"。

**轮次状态机（每个圆桌）：**

```
CREATED → INTRO(主持人开场) → ROUND[1..N] → SUMMARY(主持人总结) → DONE
             │                    │
             │                    ├─ 每轮流程：主持人抛出本轮聚焦问题 → 依次/按需点名嘉宾发言 →
             │                    │   （可选）主持人一句衔接/追问 → 进入下一轮
             └─ 异常兜底：任一 Agent JSON 不合法 → 重试1次 → 降级为纯文本发言并打标记
```

**发言人调度策略（MVP 用"点名制"，比自由抢话稳得多）：**
- 主持人每轮先生成「本轮聚焦问题 + 点名 1 位嘉宾」；
- 被点名嘉宾发言（流式）；
- 发言结束，主持人根据该发言决定：追问同一位 / 点下一位 / 结束本轮。用**结构化输出**实现（见 Prompt 文档 §3）；
- 每轮最多 3 位发言、全程最多 4 轮，硬编码上限防跑飞（兜底策略：状态机有明确的 DONE 条件，不会无限循环）。

**上下文管理（应对长对话）：**
- 每个 Agent 的 system prompt 固定（Persona + 行为约束）；
- 对话历史按「主持人视角 / 各嘉宾视角」分别裁剪：嘉宾只看到自己已说过的话 + 他人发言的摘要，超出上限（约 6k token）时对最早轮次做摘要压缩。

### 2.2 Agent 层

| Agent | 输入 | 输出（JSON Schema 强约束） |
|---|---|---|
| HostAgent | 主题、Persona 列表、历史发言 | `{type:"question"\|"transition"\|"summary", content, next_speaker}` |
| GuestAgent | Persona、主题、聚焦问题、相关历史 | `{content, stance_shift}`（stance_shift 表明是否被说服改变观点） |

- 嘉宾不是简单角色扮演：Persona 里写明**立场、专业背景、说话风格、与其他嘉宾的天然分歧点**，分歧来自 Persona 设计而非随机。
- 所有 Agent 输出先过 JSON Schema 校验（`pydantic`），失败重试一次，仍失败则降级为纯文本 + 前端显示"⚠️ 结构异常"标记（兜底策略）。

### 2.3 LLM Client

- DeepSeek `chat/completions`，`stream=True`，OpenAI 兼容 SDK；
- 每 Agent 独立请求；流式 chunk 一边解析一边经 SSE 转发；
- 关键点：**JSON 模式输出不能直接边流边发**（前端会看到原始 JSON）。方案：`content` 字段用流式，调度类字段（next_speaker 等）让模型输出后置、或对 Host 用"两段式"（先短 JSON 决策、再流式正文）；
- 超时/限流：单请求 60s 超时，失败重试 1 次，重试失败则该 Agent 发言降级为占位文本，圆桌继续（不中断直播）。

### 2.4 SSE 推流协议（前端约定的统一事件格式）

```json
{"event": "speaker_start", "data": {"speaker": "guest_1", "name": "技术乐观派"}}
{"event": "delta",         "data": {"text": "我认为..."}}
{"event": "speaker_end",   "data": {"speaker": "guest_1"}}
{"event": "thinking",      "data": {"speaker": "guest_2"}}   // 前端显示"正在思考..."动画
{"event": "round_change",  "data": {"round": 2, "focus": "落地的最大障碍是什么？"}}
{"event": "done",          "data": {"debate_id": "..."}}
{"event": "error",         "data": {"message": "...", "recoverable": true}}
```

### 2.5 数据模型（SQLite，MVP 够用且零运维）

- `personas`：id, name, avatar, stance, style, system_prompt
- `debates`：id, topic, persona_ids, status, created_at, transcript_path
- `messages`：id, debate_id, round, speaker, role, content, created_at

### 2.6 前端（Vanilla JS，MVP 不引重框架）

- 三个页面组件化拆分：`Home` / `Create` / `Live`（含 Transcript 侧栏抽屉）/ `Archive`；
- "思考中"动画：收到 `thinking` 事件后显示打字点动画；流式 `delta` 逐字渲染；
- EventSource 原生消费 SSE，断线自动重连 + 从 `messages` 表补齐缺失历史（断线兜底）。

## 3. 工程化与质量（对应作业"最重要"部分）

1. **禁止一锯子魔法 Prompt**：所有 Prompt 版本化管理在 `prompts/` 目录（YAML），带版本号与迭代记录（见 Prompt 文档）。
2. **Schema 先行**：Agent 输出 JSON Schema 定义在 `schemas/`，代码与 Prompt 共同遵守；CI 里跑 schema 一致性测试。
3. **测试**：
   - 单元：Orchestrator 状态机（mock LLM）、JSON 校验降级路径、上下文裁剪；
   - 集成：真实调 DeepSeek 跑一轮完整圆桌（冒烟，标记为 slow test）；
   - 评估（EE2E 思路）：固定 3 个测试主题 × 3 次运行，人工打分「立场对立是否真实」「是否跑题」「是否重复」，指标为交锋率 / 重复率 / 聚焦度 / 收敛性 / 立场真实性 / 人设一致性（各 0-2 分）。
4. **Git**：`main` 保护，功能按 `feat/orchestrator`、`feat/sse-stream` 等分支开发，PR 合入；commit 记录真实开发过程（作业要求"真实使用痕迹"）。
5. **错误兜底汇总**：LLM 超时/限流→重试+降级占位；JSON 不合法→重试+降级标记；SSE 断线→重连+历史补齐；轮数超限→强制 SUMMARY 收尾。**任何单点失败都不会让直播页面挂掉。**
