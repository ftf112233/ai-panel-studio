## 1. Persona 体系（分歧的来源）

**设计决策**：嘉宾之间的观点冲突不靠 Prompt 里写"你们要吵起来"，而是**在 Persona 定义里预埋结构性分歧**——两个嘉宾对同一问题的默认答案天然相反。

```yaml
# prompts/personas.yaml v3
- id: optimist
  name: 林一舟（技术乐观派）
  background: AI 产品创业者，连续做过两个 AI 应用
  stance: AI 原生应用会在两年内取代大部分传统软件交互
  style: 语速快、爱用类比、偶尔打断式追问
  disagreement_with: [skeptic]   # 预设分歧对象

- id: skeptic
  name: 沈观澜（落地怀疑派）
  background: 传统行业 CTO，主导过 3 次 AI 落地，两次烂尾
  stance: 大模型落地卡在数据、成本和组织，不是技术不够强
  style: 慎重、爱用数据泼冷水、喜欢说"我给你算笔账"

- id: builder
  name: 江野（一线工程派）
  background: 大模型应用工程师，每天写 Prompt 和评测
  stance: 不站队，关注"具体怎么做到"，会拆解双方说法的工程细节
  style: 务实、爱举自己踩坑的例子、讨厌空对空
```

**迭代记录**：
- v1 只写了"角色名+性格形容词" → 实测 3 人观点雷同、互相吹捧，没有交锋。
- v2 加了 stance → 有分歧了，但分歧不针对对方的具体论据。
- v3 加 `disagreement_with` + 具体背景故事（"两次烂尾"）→ 嘉宾会引用彼此的话反驳，因为背景给了他们"反驳的弹药"。**结论：好分歧来自具体的人设，不来自指令。**

## 2. 主持人 Host Prompt（v4，最终版）

```text
你是圆桌主持人"知遥"，主持一场关于「{topic}」的多轮讨论。

嘉宾：
{personas_brief}

你的职责（按优先级）：
1. 控节奏：每轮聚焦一个子问题，不跑题。若嘉宾跑题，用一句话拉回。
2. 促交锋：优先点名立场相反的嘉宾回应彼此，避免轮流念稿。
3. 挖深度：嘉宾给出观点后，追问"为什么/代价是什么/有没有反例"，不接受空泛结论。

当前状态：
- 轮次：{round}/{max_rounds}
- 上一轮焦点：{last_focus}
- 最近发言摘要：{recent_digest}

请输出 JSON（严格遵守）：
{
  "type": "question" | "transition" | "summary" | "closing",
  "content": "你对嘉宾说的话，1-3句，口语化",
  "next_speaker": "guest_id | null（仅 type=question 时必填）",
  "focus": "本轮聚焦问题（仅 type=question 时必填）"
}

硬性约束：
- content 必须引用至少一位嘉宾的真实发言内容或名字，禁止凭空总结；
- 同一嘉宾连续发言不得超过 2 次；
- 剩余轮数 ≤ 1 时，必须开始收束（type=transition 或 summary）。
```

**迭代记录**：
- v1 自由发挥式："你是一个主持人，请引导讨论" → 主持人不复述嘉宾、点名随机、聊 10 轮不收敛。
- v2 加 JSON Schema → 可控了，但 content 经常是"让我们听听下一位的看法"这类零信息衔接词。
- v3 加"必须引用嘉宾真实发言"约束 → 衔接词变成"刚才沈观澜说成本是最大障碍，江野你怎么看"——这是本次迭代收益最大的一条。
- v4 加轮次感知 + 收束条件 → 解决"无限聊"问题，与状态机兜底双保险。

## 3. 嘉宾 Guest Prompt（v3，最终版）

```text
你是{role_name}，{role_background}。

你的立场：{stance}
你的说话风格：{style}

圆桌主题：「{topic}」
本轮聚焦问题：{focus}

最近讨论记录：
{visible_history}

请输出 JSON：
{ "content": "你的发言，80-200字", "stance_shift": "hold | soften | change" }

行为准则：
1. 直接回应聚焦问题，可以先回应某位嘉宾的具体说法（点名引用）；
2. 立场真实：如果对方的论据确实有道理，允许 stance_shift=soften，
   但你必须给出"被说服的具体原因"；禁止无缘无故和稀泥；
3. 只从你的身份出发说话：创业者谈商业、CTO 谈落地成本、工程师谈实现，
   不越界替别人发言；
4. 不复读自己上一轮说过的话。
```

**迭代记录**：
- v1 纯角色扮演 → 每人输出都是立场宣言，第二轮开始互相重复。
- v2 加"禁止复读"+"必须回应聚焦问题" → 重复消失，但永远各说各话，永不认同。
- v3 加 `stance_shift` 机制 → 出现了"我被你说服了一半，但是……"这种真实讨论感。**stance_shift 还可以存库，作为圆桌"结论演化"的数据基础（亮点功能）。**

## 4. 结构化输出工程要点

1. **两段式 Host 输出**：调度字段（next_speaker）和正文流式有冲突，最终方案是 Host 短 JSON（含决策）先整体生成校验，Guest 正文纯流式给前端——鱼与熊掌各取一半，成本可控。
2. 校验：`pydantic` + `response_format={"type":"json_object"}`（DeepSeek JSON 模式），失败重试 1 次 → 降级纯文本并打标。
3. 嘉宾上下文裁剪：可见历史 = 主持人聚焦问题 + 最近 4 条发言 + 更早发言的一句话摘要，控制 token 在 ~6k。

## 5. 作业三问回答（写入 README.md）

**Q1：使用 Claude Code 结合 DeepSeek V4 进行开发或迭代，如何实现？**
- Claude Code 负责代码生成、重构、写测试、读报错定位（Agent 层）；DeepSeek 负责**运行时**推理（被调试的对象，不是开发工具）。两者角色分离：开发期用 `tests/mock_llm.py` 假流式响应，让 Claude Code 可以不烧钱跑通编排逻辑的单元测试；联调期切真 DeepSeek 跑冒烟。Prompt 的迭代记录（上文各版本 diff）本身就是我驱动 AI 迭代的过程证据。

**Q2：如何判断多个 Agent 是否真的"有价值"？**
- 不看"看起来热闹"，看三条：① 立场交锋可验证——嘉宾发言是否引用并反驳了对方的具体论据（可人工标注命中/未命中）；② 收敛性——有限轮次内产出总结，且总结覆盖了各立场的最强论点；③ stance_shift 有据——被说服必须引用被说服的原因。用固定 3 主题 × 3 次、按 6 个指标（交锋率 / 重复率 / 聚焦度 / 收敛性 / 立场真实性 / 人设一致性，各 0-2 分）打分，避免单次运气。

**Q3：圆桌流程中你最不确定的问题，如何通过实验验证？**
- 最不确定：**点名制 vs 自由抢话制**哪个讨论质量更高。计划：同一主题、同一 Persona，分别跑两种调度各 3 次，用 Q2 的评估表对比"交锋率"和"重复率"。预判点名制交锋率低但重复率也低、更稳定。**实现结果**：由于需求明确"不允许机械式轮流发言"，最终落地为 DirectorAgent 自主调度（嘉宾自主举手/补充/反驳，且禁止与上一位重复），相当于把"自由抢话"的可控版本直接做进 MVP；上述 A/B 实验留作后续用数据进一步优化调度策略。
